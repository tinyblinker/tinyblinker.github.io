1. 核心结论

  • 编译和解释不是互斥的程序类别. 解释器本身可以是编译后运行的程序;它运行时再读取,分析并执行另一种语言的代码.
  • 多语言代码可以组成同一个项目. 如果不同部分被编译成兼容的目标代码,并遵循相同的二进制接口约定,就可以通过链接或运行时接口相互调用.
  • 区分进程边界很重要. 两个服务通过网络通信,与两种语言的代码在同一进程里互相调用,是两种不同层次的“协作”.

2. 视频一:编译与解释代码如何共处同一程序中?

2.1. 视频主旨

视频讨论解释器和编译后的程序如何在一个项目中共存.关键点是:解释器并非“没有被编译的东西”,而是一个负责读取并执行其他代码的程序.解释器自身通常也需要先由编译器构建.
因此,一个应用可以由编译后的主体程序构成,同时嵌入解释器,让应用在运行时执行脚本.这里的“编译”和“解释”发生在不同的代码或不同的阶段,并不矛盾.

2.2. 关键概念

  • 编译器:把一种语言的源代码转换成另一种表示,例如汇编,目标文件,字节码或机器码.
  • 解释器:读取某种语言的程序,并按照该语言的规则执行它.实现方式可以不同:有的直接执行语法结构,有的先生成字节码,再由虚拟机执行.
  • 运行时:程序执行期间提供的环境,例如解释器,垃圾回收器,标准库和动态加载机制.
  • 嵌入式解释器:作为一个组件运行在宿主应用之中,由宿主程序调用其接口来执行脚本.

2.3. 具体例子:用 Python 脚本扩展一个 C 程序

假设一个图像处理应用用 C 编写,要求运行速度快,但又希望用户能自定义处理流程.

用户脚本(Python)
        |
        v
应用中的 Python 解释器
        |
        v
C 编写的图像处理程序

可能的运行过程:

  1. 开发者把 C 应用编译成可执行程序.
  2. 程序启动时,加载或初始化 Python 解释器.
  3. 用户提供一个 Python 脚本,例如“把图片变成灰度图”.
  4. C 程序调用解释器接口,让解释器执行脚本.
  5. 脚本通过宿主应用提供的函数调用图像处理能力.

此时,应用的主体是编译后运行的 C 程序;脚本则是在运行时由解释器处理的 Python 代码.它们处在同一个应用架构中,但执行路径不同.

2.4. Python 的例子:解释器本身也可以是编译出来的

以常见的 CPython 实现为例,可以把过程简化理解为:

Python 源代码
    |
    v
解析与编译阶段
    |
    v
字节码
    |
    v
CPython 虚拟机执行

CPython 解释器实现本身主要由 C 代码构成,通常先编译成可执行程序;这个程序运行后,才负责处理 Python 程序.因而,“解释器是编译出来的程序”与“它解释执行 Python 代码”可以同时成立.

2.5. 本节重点

  • “编译型语言”和“解释型语言”是对常见实现方式的概括,不代表两类程序完全不能组合.
  • 问“程序是不是编译的”时,要先明确指的是哪段代码:解释器本身,应用主体,还是用户脚本.
  • 嵌入解释器常用于脚本扩展,插件,自动化和可配置逻辑.
  • 把脚本交给解释器执行,并不意味着整个应用的所有代码都必须采用解释执行.

3. 视频二:为什么有些项目会使用多种编程语言?

3.1. 视频主旨

视频说明项目采用多种语言的原因,以及这些语言如何在系统层面协作.语言选择往往是权衡:不同语言在性能,开发效率,生态,硬件访问和现有代码复用方面各有优势.

视频也区分了两种常见情形:

  • 不同语言的组件运行在不同进程中,通过网络等方式通信.
  • 不同语言的代码在同一个进程中协作,通常需要编译,链接,运行时或外部函数接口等机制.

3.2. 为什么项目要混用语言?

  • 性能:将计算密集或对延迟敏感的部分交给较低层语言实现.
  • 复用生态与既有代码:继续使用成熟的库或历史代码,避免从头重写.
  • 开发效率:用高级语言实现业务逻辑,脚本或快速迭代部分.
  • 系统能力:需要直接处理硬件,内存,操作系统接口或特殊运行环境时,低层语言可能更合适.
  • 逐步迁移:可以先替换某个模块,而不是一次性重写整个项目.

混用语言不是目的本身.它只有在某种优势值得承担接口复杂度,构建成本和调试成本时才有意义.

3.3. 两种“多语言协作”:跨进程与同进程

3.3.1. 1. 不同进程之间:通过协议通信

例如,一个网站可能由 Python 后端提供服务,浏览器端使用 HTML,CSS 和 JavaScript.

浏览器进程                           服务器进程
HTML / CSS / JavaScript  --HTTP-->   Python 后端

两侧通过 HTTP 等协议交换请求和响应.这里通常不要求两种语言的代码被链接成同一个可执行文件;它们之间的边界是网络协议和数据格式.

3.3.2. 2. 同一进程之内:通过函数或库接口协作

例如,Python 程序调用 C 编写的数值计算库:

Python 应用
    |
    | 外部函数接口(FFI)
    v
C 函数 / 动态库

这类调用通常发生在同一进程地址空间内.调用方和被调用方需要约定如何传递参数,返回结果,表示数据结构以及管理内存.

3.4. 编译与链接:多语言如何组合成可执行程序?

以常见的 C 工具链为例,流程可以简化为:

源代码
  |
  v
预处理
  |
  v
编译:生成汇编或中间表示
  |
  v
汇编:生成目标文件
  |
  v
链接:组合目标文件与库
  |
  v
可执行文件
  • 预处理:处理宏,条件编译和头文件等.
  • 编译:检查并转换源代码;编译器可能先生成汇编或中间表示.
  • 汇编:将汇编指令转换为机器码,通常产出目标文件.
  • 链接:组合目标文件和库,解析函数,变量等符号引用,并生成最终程序.

不同语言可以各自使用相应的编译器,生成可供链接的目标文件.链接器并不需要“理解”每种语言的高级语法;它主要处理目标文件,符号和地址等信息.

3.5. 例子:Rust 调用 C 函数

假设 C 库提供一个加法函数:

int add(int a, int b) {
  return a + b;
}

Rust 程序可以通过外部函数声明调用它.概念上,步骤是:

  1. 把 C 代码编译成目标文件或库.
  2. 在 Rust 侧声明外部函数.
  3. 构建时把 C 库链接进程序,或在运行时加载相应动态库.
  4. 调用时按双方约定传递两个整数并接收返回值.

这能够成功,不只是因为 C 和 Rust 最终都能产生机器码;还因为双方需要遵循兼容的调用约定和数据表示规则.

3.6. ABI:语言之间的“二进制合同”

ABI(Application Binary Interface,应用程序二进制接口)规定了编译后组件如何互相配合.常见内容包括:

  • 函数参数如何传递,例如通过寄存器还是栈.
  • 返回值如何传递.
  • 结构体,枚举等数据如何在内存中布局.
  • 函数名如何编码.
  • 异常,线程局部数据等运行时机制如何处理.

可以把 ABI 想成双方必须遵守的插头规格:即使两个组件都已经编译成机器码,如果“插头”规格不一致,也可能无法正确连接.

3.6.1. 简化例子:结构体布局

C 侧定义了一个包含整数和浮点数的结构体.如果 Rust 侧按不同顺序,对齐或填充规则解释同一块内存,就可能读错数据.跨语言共享结构体时,通常需要明确规定布局,不能只依赖两种语言中看起来相似的类型定义.

3.7. 静态链接与动态链接

  • 静态链接:把所需的库代码纳入最终可执行文件.通常更自包含,但文件可能更大,更新库时往往需要重新构建程序.
  • 动态链接:程序运行时加载共享库,例如 Linux 上常见的 .so 文件,Windows 上的 .dll 文件.可减少重复打包,但运行环境需要提供兼容的库.

3.8. 本节重点

  • 多语言项目需要解决的不只是“怎样把不同源文件编译掉”,还包括接口,数据布局,依赖和运行时问题.
  • 跨进程协作通常通过网络协议或进程间通信;同进程协作通常涉及链接,动态库或 FFI.
  • 同一种语言并不自动保证二进制接口兼容;不同编译器,平台和构建设置也可能影响兼容性.
  • 多语言设计要看收益是否值得:性能,复用和灵活性,是否足以抵消接口与维护成本.

5. 复习提纲

  1. 解释器本身可以先被编译,再解释执行其他语言的代码.
  2. 混合项目可以通过脚本解释执行,也可以通过目标文件链接或 FFI 调用.
  3. 跨进程通信与同进程跨语言调用不是一回事.
  4. 编译器,汇编器和链接器分别处理不同阶段.
  5. 跨语言调用必须重视 ABI:调用约定,数据布局和运行时约定.
  6. 混用语言的价值在于用合适的工具处理不同问题,而不是语言数量越多越好.
