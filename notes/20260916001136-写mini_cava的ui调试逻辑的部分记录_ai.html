1. 第一部分:ring buffer「装不进数据」的假象

1.1. 一句话结论

ring buffer 本身 从头到尾都没坏*。真正的问题是消费者在 *空转
(busy-loop 无脑 pop_slice),消费速度远快于生产者(音频回调)的填充速度,
所以绝大多数 pop_slice 都返回 0,*看起来* 就像 buffer 不工作。

1.2. 现象

  • 控制台疯狂刷屏:

    Consuming fft input data too quickly!!
poped_data_len = 0
  • 但最初几次 poped_data_len = 1024,之后就一直 = 0。
  • 于是直觉判断:「ring buffer 没有把数据传过来」。

1.3. 根因分析

1.3.1. 数据流的两端速率不匹配

  • 生产者:CPAL 音频回调,每 ~21ms 才来一批(~2048 个采样)。
  • 消费者:一个 loop { pop_slice; FFT } 的 无等待空转,
    每秒钟能空跑几千次。
  • 结果:消费者先把预填充的数据瞬间吃光,之后每次醒来看 buffer 都是
    空的/不满的,于是返回 0 或部分数据。

1.3.2. 关键证据(用数字说话)

在同一台机器上跑 3 秒并统计日志:

producer 回调次数(pushed_slice_cnt = 2048):  138 次   <- 一直在产
consumer 成功 pop 满 1024 的次数:               280 次   <- 有数据时能吃满
consumer 空转 pop=0 的次数:                    21983 次  <- 空转才是大头
  • 138 × 2048 ≈ 282k 个采样,与 280 × 1024 ≈ 286k 基本吻合,
    说明 *数据一字不差地通过了 ring buffer*。
  • 那 21983 次空转,才是「poped_data_len 始终 = 0」的假象来源。

1.3.3. 为什么容易误判

  • 只盯着消费者一侧的打印,没去看生产者那一侧。
  • 预填充的 4096 个 ~EQUILIBRIUM~(静音)数据,让程序「前几次能吃到
    1024、之后就 0」,这个「先有后无」的现象极具迷惑性。

1.4. 调试心路历程(复盘)

  1. 先别急着改代码,先分清「谁没工作」。
    ring buffer 是 SPSC 的两端,必须 分别 验证生产端和消费端:
    • 生产端:给回调加计数,看它到底有没有被调用、每次 push 多少。
      结果:138 次、每次完整 push 2048,生产端完全正常。
    • 消费端:统计 pop 返回值分布。
      结果:有数据时能 pop 满,但空转次数是有效次数的 ~78 倍。
  2. 把「症状」翻译成「速率不匹配」。
    • 「pop 返回 0」≠「没数据」,也可能是「我来早了 / 我吃太快了」。
  3. 对照上游 CPAL 的 fft 例子。
    • 老版本 cpal 的 examples/fft.rs 用的是「先 consumer.len() 判断,
      不够就 continue 等」的写法;正是缺了这一步「等」。
  4. 注意 ringbuf 版本 API 差异。
    • consumer.len() 在 ringbuf 0.5 里变成了 consumer.occupied_len(),
      HeapRb::new().split() 拆出 producer/consumer 是对的,但需要把
      Observer 也引入作用域才能调 ~occupied_len()~。

1.5. 修复

消费者改成「先等够 FFT_SIZE 个采样,再一次性吃满」:

while consumer.occupied_len() < FFT_SIZE {
    std::thread::sleep(std::time::Duration::from_millis(1));
}
let mut window = [T::EQUILIBRIUM; FFT_SIZE];
consumer.pop_slice(&mut window);
  • 去掉了导致误解的预填充。
  • 去掉了刷屏的 per-callback println!,峰值信息每 50 帧打印一次。

1.6. 验证(端到端)

用一个 1000 Hz 的正弦波打到 default_sink,看 FFT 能否抓到:

ffmpeg -f lavfi -i "sine=frequency=1000:sample_rate=48000:duration=8" \
       -ac 2 -ar 48000 tone.wav
pw-play tone.wav

峰值稳定出现在预期 bin,说明真实音频数据已经
从设备 → 回调 → ring buffer → 消费者 → FFT 全链路跑通。

1.7. 经验教训(可复用)

  1. 调 SPSC/队列问题时,*一定要分别给生产端和消费端加计数*,
    用「总产量 ≈ 总消费量」来判断到底哪一端有问题。
  2. 「返回 0」要多问一句:是「真没数据」,还是「消费者太快 / 生产者太慢」。
  3. 消费者不要在热循环里无脑 pop;要么阻塞/休眠等待,
    要么用「攒够一批再处理」的批量策略。
  4. 参考上游例子时,先核对依赖版本,API 可能已经改名
    (len → occupied_len,~push~ → try_push/push_slice 等)。
  5. 用真实信号(正弦波)做端到端验证,比「看打印」更有说服力。

1.8. 遗留建议

  • 输入是 2 声道交错(L,R,L,R…),直接塞进 FFT 会把 L/R 混在一起,
    峰值频点会偏移。做频谱可视化前建议先「降混成单声道」(取 (L+R)/2)再 FFT。
  • 1ms 的 sleep 对可视化足够,追求更低延迟可换成 condvar 或定时器驱动。

2. 第二部分:用 crossterm 画 cava 式频谱条

2.1. 需求

基于一个不断变化的 ~Vec<f32>~(FFT 半频谱)画出类似 cava 的频谱条。

2.2. 实现方案对比

  1. *整帧字符串*(最简):把整帧拼成一个 String,~MoveTo(0,0)~ 一次打印,
    几乎无闪烁。
  2. *逐列 diff 渲染*(最终采用):维护上一帧的缓存,只重绘变化的格子,
    用绝对光标定位,避免 raw mode 下 OPOST 关闭导致的错位。

2.3. 渲染结构

  • 每根柱子 3 列宽 + 1 列空隙。
  • 柱子用 8 级填充字符(▁▂▃▄▅▆▇█)表示 1/8 格精度。
  • 懒渲染:仅字符/颜色与上一帧不同的格子才重绘。

3. 第三部分:频谱条为什么「又高又平」

3.1. 现象

柱子几乎不动、看起来都差不多高,没有 cava 那种高低错落、会跳舞的感觉。

3.2. 日志数据分析(my_cava.log)

  • 变量:~normed_half_db_data~,512 个 dB 值,共 221 帧(约 4 秒)。
  • 前 ~50 帧全是 -240(纯静音),之后才有真实音频。
  • 有声音后:最响 bin 约 -9~-18 dB,中位数约 -57 dB,均值约 *-92 dB*。
  • 关键结论:真实音乐只在约 [-60, -10] dB 这 50 dB 内波动,
    -240 这个地板只有真空隙的高频 bin 才会触达。

3.3. 根因(三个原因叠加)

3.3.1. 原因 1(主因):dB 范围假设错了

原映射 mapped = (avg + 240) / 240,把 [-240, 0] dB 线性摊到 [0,1]。
但音频永远到不了 -240 dB,真实动态范围只有 ~50 dB,于是:

  • -15 dB → 0.94,-40 dB → 0.83,-70 dB → 0.71。
  • 所有有声音的柱子全被挤在 71%~95% 高度,看着又高又平。
  • 好比拿一把 2.4 米长的尺子去量一个 50 厘米的东西,全集中在尺子顶端。

3.3.2. 原因 2(次因):平均化稀释峰值

极端弯曲的对数映射让第 0 根柱覆盖 62 个 bin,一平均就把 -13 dB 的尖峰拉到 -38 dB。

3.3.3. 原因 3(小问题):在 dB 域求平均

dB 是凹函数,平均(dB) ≠ dB(平均幅度),会系统性偏向小声的 bin。

4. 第四部分:改进方案(A → E)

4.1. 方案 A:缩小 dB 地板(一行见效)

const DB_FLOOR: f32 = -60.0;
let mapped = ((avg - DB_FLOOR) / (-DB_FLOOR)).clamp(0.0, 1.0);

-15 dB → 0.75,-40 dB → 0.33,-70 dB → 0,动态范围立刻拉开。

4.2. 方案 B:autosens(每帧归一化,cava 的灵魂)

cava 不平缓的核心在于它 *每帧自动调增益,让最高柱子刚好顶到屏幕顶端*。

  • 第一遍算出所有柱子的原始强度,找出本帧最大值。
  • 峰值超了就快速降增益,不足就缓慢升增益(滚动最大值,避免抖动)。

4.3. 方案 C:用 max 代替 avg

区间取最大幅值,尖峰不被稀释,柱子弹跳更明显。

4.4. 方案 D:gravity 幂次曲线

mapped.powf(GRAVITY),GRAVITY > 1 让小声柱子相对更矮,高低差更明显。

4.5. 方案 E:频率映射

把 LOG_BASE 指数映射换成按实际频率的对数分布(见下一节)。

5. 第五部分:右侧柱子「几乎不显示」

5.1. 根因

把 LOG_BASE 改成 10.0 后,旧映射 (10^t - 1) / 9 变成 凸 曲线,
大部分柱子被推到 5.7k~24kHz(奈奎斯特)这一段。而真实音频能量集中在低频,
10k~24kHz 基本是 FFT 噪声(日志里就是 -240 dB),所以右侧永远空着。

5.2. 修复:cava 式频率映射

放弃 log_bin_index,改成按实际频率对数分布,柱子覆盖 40Hz ~ 10kHz
(cava 默认 lower_cutoff_freq=50 / higher_cutoff_freq=10000):

fn bar_to_bin(s: usize, bars: usize, freq_atom: f32) -> usize {
    let t = s as f32 / bars as f32;
    let freq = LOWER_CUTOFF_FREQ * (HIGHER_CUTOFF_FREQ / LOWER_CUTOFF_FREQ).powf(t);
    (freq / freq_atom) as usize
}

这样右侧柱子对应 5k~10kHz(镲片、齿音等真实内容),就能显示了。

6. 第六部分:柱顶坠格 + 渐变配色

6.1. 柱顶坠格(峰值回落)

  • 每根柱顶加 CAP_SIZE 个全字符块。
  • 柱子涨时坠格跟上去,柱子跌时坠格 更慢地 下落(CAP_GRAVITY 0.15 格/帧,
    远小于柱子的下降速度),形成「漂浮的峰值残影」。

6.2. 渐变配色

  • 垂直渐变:绿 → 黄 → 红(底部 → 顶部)。
  • 初版按 屏幕绝对高度 归一化,矮柱子只能看到绿色段;
    后改为按 柱子自身平滑后的高度 归一化,每根柱子都能跑满整段渐变,
    柱高每帧变化时整段渐变随之伸缩。

7. 第七部分:最终管线回顾

  1. cpal 从 PipeWire default_sink monitor 采集音频。
  2. ringbuf 传递 PCM 数据(生产端:音频回调;消费端:FFT)。
  3. rustfft 做 1024 点 FFT,先降混(2 声道取 (L+R)/2)、再加汉宁窗。
  4. 幅度 → dB:=20 * log10(norm / window_sum)=。
  5. 频率映射(40Hz~10kHz)→ 区间取最大 → dB 映射(-60 floor)→ gravity。
  6. autosens 归一化 → attack/decay 平滑 → 柱高 + 坠格 → 渐变着色 → crossterm 绘制。
