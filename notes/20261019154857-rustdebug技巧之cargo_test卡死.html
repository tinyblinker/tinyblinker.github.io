1. 适用场景

当 cargo test 出现以下情况时,可以参考本手册:

  • 终端长时间没有输出,命令不返回
  • 测试进程占用大量 CPU,但一直没有结果
  • 不知道是哪个测试卡住
  • 不知道是死循环,死锁,还是在等待 IO
  • 想在不依赖 AI 的情况下,用系统工具定位根因

核心原则:

  1. 不要直接运行没有超时保护的完整测试套件.
  2. 先编译,后运行,先缩小范围,再深入.
  3. 先判断“忙等”还是“等待”,再选择排查工具.
  4. 用调用栈和源码定位,不靠猜.
  5. 对每个循环检查“退出条件”和“每轮是否推进状态”.

2. 排查步骤

2.1. 第 1 步:只编译,不运行

先确认问题不是编译错误,同时拿到测试二进制路径:

cd /home/shyweeds/Projects/lisp_rs
cargo test --no-run

输出示例:

Executable unittests src/lib.rs (target/debug/deps/my_lisp-8f18af13d95c8e05)

cargo test --no-run 只编译,不会执行测试,所以不会因为死循环卡住.

后续尽量直接运行这个测试二进制,原因:

  • 不受 Cargo 外层进程干扰
  • 更容易配合 timeout, gdb, perf, strace
  • 退出码和信号更直观

2.2. 第 2 步:列出测试

./target/debug/deps/my_lisp-8f18af13d95c8e05 --list

确认测试名称和数量,为下一步过滤做准备.

2.3. 第 3 步:串行运行并加超时

不要一上来跑全部测试.先按关键字缩小范围:

timeout 5 ./target/debug/deps/my_lisp-8f18af13d95c8e05 \
        --test-threads=1 --nocapture test_tokenize

关键参数:

  • timeout 5:5 秒后强制终止,避免终端一直卡住.
  • --test-threads=1:一次只跑一个测试,保证最后打印的测试就是卡住的那个.
  • --nocapture:测试名实时输出,而不是等测试结束后才显示.
  • test_tokenize:测试名过滤,只运行名称中包含该字符串的测试.

如果输出停在:

running 7 tests
test tests::test_tokenize_comments ...

然后进程被终止,退出码为 124,说明:

  • 124 是 timeout 的退出码,表示超时
  • test_tokenize_comment 就是卡住的测试

2.4. 第 4 步:用过滤和跳过继续缩小范围

精确运行单个测试:

timeout 3 ./target/debug/deps/my_lisp-8f18af13d95c8e05 \
        --exact tests::test_tokenize_comment
echo $?   # 124 表示超时

跳过已知会卡住的测试,验证其余测试是否正常:

timeout 60 ./target/debug/deps/my_lisp-8f18af13d95c8e05 \
        --skip test_tokenize_comment \
        --skip test_tokenize_comments

如果输出:

test result: ok. 52 passed; 0 failed; 0 ignored; 2 filtered out

就可以确定:问题只集中在被跳过的测试,而不是整个测试环境或 Cargo 配置.

2.5. 第 5 步:判断是忙等还是等待

在后台启动会卡住的测试:

./target/debug/deps/my_lisp-8f18af13d95c8e05 \
    --exact tests::test_tokenize_comment &

pid=$!

观察线程 CPU:

top -H -p "$pid"

或者:

ps -L -o pid,tid,pcpu,stat,comm -p "$pid"

判断方法:

现象 更可能的原因
某线程接近 100% CPU,状态 R 用户态死循环 / 忙等
所有线程接近 0% CPU 死锁,锁等待,IO 阻塞
线程状态 S/D,系统调用不返回 等待 IO,网络,子进程等
进程存在但完全没有输出 也可能是测试根本没启动

本案例中,测试线程持续占用 CPU,因此优先怀疑死循环.

2.6. 第 6 步:用 gdb 抓调用栈

这是定位卡死最直接的方法.让测试跑几秒,然后用 SIGINT 中断并打印所有线程栈:

timeout -s INT 5 gdb -q -batch \
        -ex 'set pagination off' \
        -ex 'run --exact tests::test_tokenize_comment' \
        -ex 'thread apply all bt' \
        --args ./target/debug/deps/my_lisp-8f18af13d95c8e05

参数说明:

  • timeout -s INT 5:5 秒后发送 SIGINT,相当于在 gdb 里按 Ctrl-C
  • run --exact ...:在 gdb 中启动测试
  • thread apply all bt:打印所有线程的 backtrace
  • --args:后面的内容作为被调试程序的参数

本案例实际抓到的关键栈:

Thread 2 ...
#2  Peekable<CharIndices>::peek
#3  my_lisp::lexer::tokenize at src/lexer.rs:26
#4  my_lisp::tests::test_tokenize_comment at src/lib.rs:746

从栈可以直接读出:

  • 测试函数是 test_tokenize_comment
  • 它调用了 my_lisp::lexer::tokenize
  • 卡住的位置是 src/lexer.rs:26
  • 对应源码是 chars.peek()

如果 gdb 停在别的线程,可以先查看线程列表:

(gdb) info threads
(gdb) thread 2
(gdb) bt
(gdb) frame 3
(gdb) info locals
(gdb) list

其中:

  • info threads:查看所有线程
  • thread N:切换到可疑线程
  • bt:查看当前线程调用栈
  • frame N:切换到某个栈帧
  • info locals:查看局部变量
  • list:显示当前源码上下文

注意:应使用带调试信息的 dev 构建,不要用 --release,否则行号和局部变量可能不可用.

2.7. 第 7 步:gdb 不可用时的替代工具

2.7.1. perf:找热点函数

perf top -p "$pid"

如果死循环在用户态,通常会看到某个函数长期排在热点第一位,例如:

my_lisp::lexer::tokenize

也可以采样后生成报告:

perf record -g -p "$pid" -- sleep 3
perf report

2.7.2. strace:判断是否在等待系统调用

strace -p "$pid"

判断方法:

  • 几乎没有系统调用输出,CPU 又很高:用户态死循环
  • 反复输出同一类系统调用:可能在重试或忙等 IO
  • 停在 futex, read, poll, connect 等调用:可能在等待锁或 IO

2.7.3. 临时日志:确认循环是否在重复

如果无法使用调试器,可以在可疑循环里临时加入日志:

eprintln!("loop: peek={:?}", chars.peek());

如果日志以相同内容无限重复,就可以确认死循环.

注意:临时日志只用于定位,定位后应删除,不要留在正式代码里.

2.8. 第 8 步:回到源码,检查循环的退出条件和进展

拿到源码行号后,不要只看那一行,要检查整个循环:

  • 循环有哪些退出路径?
  • 每个退出条件是否覆盖所有边界情况?
  • 每一轮循环是否让状态向退出条件前进?
  • 输入耗尽(EOF)时会发生什么?
  • 空输入,无换行,未闭合括号,未闭合字符串分别会怎样?

本案例中的问题代码位于 src/lexer.rs:25-32:

';' => loop {
    if let Some((_, c)) = chars.peek() {
        if *c == '\n' {
            break;
        }
        chars.next();
    }
},

逐步分析:

  1. 读到分号 ; 后进入 loop.
  2. 只要 chars.peek() 返回 Some,就继续跳过注释字符.
  3. 遇到换行符时 break.
  4. 如果注释一直持续到输入末尾,=chars.peek()= 返回 None.
  5. if let Some(...) 匹配失败,循环体什么都不做.
  6. 没有 break,也没有推进迭代器.
  7. 下一轮 peek() 仍然返回 None.
  8. 永远重复,形成死循环.

对应的两个测试输入都没有末尾换行:

tokenize("(+ 1 2) ; this is the comment")
tokenize("(+ 1 2) ; This is a comment")

如果注释后面有换行,循环会正常退出:

tokenize("(+ 1 2) ; this is the comment\n")

因此可以确认:问题不是解析器,不是环境查找,不是测试框架,而是 lexer 的注释分支没有处理 EOF.

2.9. 第 9 步:用最小输入验证根因

写一个最小复现,分别测试“有换行”和“无换行”:

tokenize("; comment\n") // 正常结束
tokenize("; comment")   // 卡死

如果结果与预期一致,就完成了根因验证.

也可以检查其他边界输入:

  • 空字符串
  • 只有空白字符
  • 注释在开头
  • 注释在中间
  • 注释在末尾且无换行
  • 未闭合的括号
  • 未闭合的字符串

2.10. 第 10 步:修复并回归

修复时应该修根因,而不是修改测试输入绕过问题.

一种写法是使用 while let,让 EOF 自然结束循环:

';' => {
    while let Some((_, c)) = chars.peek() {
        if *c == '\n' {
            break;
        }
        chars.next();
    }
}

另一种写法是显式处理 None:

';' => loop {
    match chars.peek() {
        Some((_, '\n')) => break,
        Some(_) => {
            chars.next();
        }
        None => break, // 注释一直到文件末尾
    }
},

修复后至少验证:

cargo test
cargo test tokenize

并确认原来的两个测试都能正常结束,不再依赖 timeout.

3. 本案例结论

  • 项目路径: /home/shyweeds/Projects/lisp_rs
  • 现象: cargo test 不返回,进程持续占用 CPU
  • 卡住的测试:
    • test_tokenize_comment
    • test_tokenize_comments
  • 根因位置:=src/lexer.rs:25-32= 的注释处理分支
  • 根因:注释一直持续到文件末尾时,=chars.peek()= 返回 None,循环没有退出路径
  • 其余 52 个测试全部通过,说明问题范围仅限 lexer 注释分支

6. 经验总结

  • 卡死不是断言失败:测试框架会一直等待未结束的测试,所以即使其他测试通过, cargo test 也不会返回.
  • 并行测试会掩盖卡住的测试名:默认多线程运行时输出交错,应该用 --test-threads=1.
  • CPU 使用率是重要线索:高 CPU 优先怀疑死循环,低 CPU 优先怀疑死锁或 IO.
  • 调用栈比猜测可靠:gdb 的 backtrace 可以直接给出文件,行号和函数名.
  • 每个 loop 都要有明确的退出路径:特别是处理 EOF,空输入,错误输入时.
  • 循环必须每轮都有进展:如果某一轮没有推进状态,也没有退出,就会无限循环.
  • 测试输入应覆盖边界:注释在文件末尾,空输入,未闭合结构都应该有对应用例.
